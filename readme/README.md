# 对账引擎 · 交付说明

**一句话**：给一份需求清单和一个代码仓库，逐条回答「要求做的，代码里做了吗」——每条结论都给 `文件:行` 和搜索轨迹，查过哪里、没查到哪里。

## 交付包结构

赛事要求的五个目录与本仓库的对应关系：

| 目录 | 内容 | 本仓库位置 |
|---|---|---|
| `readme/` | 总览 / 环境与安装 / 运行步骤 / 开源组件 / 码道应用总结 | 本目录 |
| `project/` | 可运行源码（引擎 + CLI + 本地演示前端） | `gap-engine/`；口径与评测文档在 `对账引擎/` |
| `ppt/` | 答辩用 PPT（场景 / 架构 / 亮点 / 码道应用 / 指标与边界） | 页级大纲见 `ppt/PPT大纲.md`（同批交付） |
| `video/` | ≤ 3 分钟演示 | 分镜与旁白见 `video/脚本.md`（同批交付） |
| `codearts_proof/` | 码道交互留痕，按天归档 | `codearts_proof/daily/D0.md` 起 |

## 它输出什么

三态结论，不存在第四种：

| 结论 | 含义 | 必须附带 |
|---|---|---|
| `supported` | 找到支持证据 | `file:line` 定位 |
| `contradicted` | 代码里有**显式否定声明**，与要求不一致 | `file:line` 定位 |
| `no_evidence` | 我找过这些地方，没找到 | `search_trace`（查过几类、几处） |

判定域只有 `performance` / `concurrency` / `feature` / `testing` 四类；其余类型标"不判定"并写明原因。七类识别与四类判定的书面理由、以及「识别七类为什么只判四类」的答辩口径见 `contract/scope.md`（仓库中为 `gap-engine/contract/scope.md`，交付包中为 `project/contract/scope.md`）。

## 30 秒验证

```bash
pip install -e gap-engine
gap --help
gap spec gap-engine/contract/fixtures/fx-contradicted --spec gap-engine/contract/fixtures/fx-contradicted/requirements.md
```

最后一条默认产出 `reports/fx-contradicted-spec.md`（`gap spec` 不带 `--out` 时的命名规则是 `<仓库目录名>-spec.md`），其中包含 `结论：代码里有反证，与要求不一致` 与 `- 定位：app.py:9`。带 `--out` 可指定文件名，`tests/test_fixtures.py` 就是用这种方式生成受守卫的六份报告。

## 引擎质量实测（人工真值标注，N 明确）

这组数字**不依赖作者回执**：把公开库文档里的功能自述写成需求清单，跑 `gap spec`，再逐条到代码里定真值，最后统计引擎判对/判错。全部样本、逐条标注与引擎原始报告都在交付包的 `project/评测-引擎质量/`（源码仓库内为 `对账引擎/评测-引擎质量/`），可用同目录 `README.md` 里的命令复跑。

| 样本 | 条数 | 引擎结论 | 怎么读 |
|---|---|---|---|
| 真实现（filelock 20 + 三个纯库 12） | 32 | 有证据 8 / 没找到证据 19 / 有反证 0，另 4 条不判定 + 1 条不可验收 | precision **8/8 = 100%**（分母 = 引擎下了确定判断的条数）；recall **8/32 = 25%**（按可判 27 条算 29.6%） |
| 真反证（从代码「显式不支持」声明反向构造） | 30 | 有反证 1 / 有证据 6 / 没找到证据 23 | 反证召回 **1/30 = 3.3%**；唯一定位 **1/1 = 100%**；反向错误 **6/30 = 20%**；漏报 **23/30 = 76.7%** |

四件事必须一起说，缺一条都会误导：

1. precision 100% 的分母只有 8；主要短板是**漏报 19 条**，不是误报。
2. 反证召回只有 1/30，且这 30 条只覆盖「代码里明写不支持」的情形，覆盖面本身有偏。同一批 30 条在判据修复前（`C-MATCHER@9`）反向错误是 18/30 = 60%，修复后（`@10`）是 6/30 = 20%——**反证指标对判据版本极度敏感，引用必须带版本号**（10 条版 `@8` 为 2/10 = 20%、召回 1/10 = 10%）。
3. 32 条真实现的真值全取自作者自述，**只能衡量「能不能找到证据」，测不到「能不能识别未实现」**。
4. 「5 条不判定」是两种机制：1 条**不可验收**（无验收标准）+ 4 条 **`out_of_scope`**（安全类，按判定域设计拒答），对外必须分开讲。

结论只限这组样本：当前版本**敢说的 8 条全对，但 32 条里 19 条没找到证据**；反证能力仍是短板（30 条反证只报出 1 条，反向错误 6 条）。

## 边界（不做什么）

- **不执行被测代码**：只读文本，不导入、不安装被测仓库的任何依赖。
- **不猜语义**：`contradicted` 只认显式否定声明（`extractors/negation.py`），不做语义推断；与需求无关的否定不算。
- **不补实现**：Healer / Verifier（生成补齐物并验证）仍是 roadmap，材料里不写成已完成。
- **七指标待回执**：认可率 / 定位率 / 漏报率 / 误报率等需要 5 份需求清单的作者回执后统计，未回执前一律写 `N=?`，不写估算值（见 `run.md` 的 `gap score`）。上一节「引擎质量实测」是另一组数字，分母口径不同，两组不得混用。
