## P2 · 场景背景：同一个问题有两面（创新性与价值）

要点：
- 老师 / 负责人拿着一份 20 条要求，只能逐条翻代码——**要求方核不动**

- 这件事在课程设计 / 大创结题 / 外包交付 / 面试 / 开源 README 里重复发生
- 不问"这段代码写得好不好"，问"**要求做的，做了吗，能证明吗**"

## P3 · 红海与空位：契约二分（创新性与价值）

要点：
- **行为契约**（OpenAPI / Pact / schemathesis 3,777★）说"路径存在、参数类型、响应 schema"——**一条规则能判，我们不碰**
- **能力契约**（"支持 500 并发""P95 < 300ms""可用性 99.9%"）需要**一组证据**，而且**不知道该找哪一组**——**这才是我们的地方**
- OpenSLO 有 1,542★ 规范与完整生成生态，**验证类工具 0 个**；但它是商业方向（用户是大厂 SRE），只进 roadmap
- 自检口径：**一条证据就能判的都不是我们的活；需要一组证据且不知找哪一组的，都是我们的活**
- 代码里已落地：分类器认七类，**判定域只开四类**

引用产物：`相关工作.md`（§五 五个前车之鉴 / §六 契约二分）；`gap-engine/src/gap_engine/schema.py`

## P4 · 产品定义：输入、输出、一条命令（技术实现）

要点：
- 输入：`一份需求清单（Markdown 列表）+ 一个代码仓库`
- 命令：`gap spec <repo> --spec <requirements.md>`（副模式 `gap analyze <repo>` 读 README 自我声称）
- 输出六样：① 需求可判定性预检 ② 这个项目实际是什么 ③ 需求 ↔ 证据对照表 ④ 会被追问的问题 ⑤ 最小补齐行动 ⑥ 可直接应用的补齐物（**⑥ 属 roadmap**）
- **双方都能跑**：交差方看"我还差什么"，验收方看"他还差什么"，同一段代码、同一引擎、同一份轨迹
- 只读仓库：不执行、不导入被测代码

引用产物：`gap-engine/reports/fx-spec.md`（输出样例）；`readme/run.md`

## P5 · 功能架构：一次对账的数据流（技术实现）

要点：
- 入站适配（Markdown → `Claim` schema）→ **Claimer**（抽条目 + 七类分类）→ **Prober**（9 个规则抽取器，含 `artifact` / `negation`）→ **Matcher**（三态 + 置信度）→ **Renderer**（报告）
- 三态：`supported` / `contradicted` / `no_evidence`（**没有第四态**；"部分支持"只是 `no_evidence` 的措辞）
- 证据单元带 `file:line`；搜不到也要输出 **`search_trace`**（查过哪几类、扫过几处、命中几处）
- Agent 现状（口径统一）：**7 个 Agent 位 = 5 个已实现（Claimer / Prober / Matcher / Challenger（规则版）/ Renderer）+ 2 个 roadmap（Healer / Verifier）**；`baseline` 先验是 Matcher 内部机制，不占 Agent 位（其数值为**先验值**，未实测；实测值由 `tools/measure_prevalence.py` 产出后标「实测，N=?」，两者不得混用）
- 真值由**需求提出人**判（对 / 错 / 说不清），不是我们自己标

引用产物：`对账引擎/施工图-对账引擎.md` §0–§1.6

## P6 · 核心亮点①：输出 ≠ 证据（技术实现 / 创新性）

要点：
- 每条结论必须给两样之一：**断言 → `file:line`**；**没找到 → `search_trace`**
- 什么都没查到的也输出，标 `coverage=none`，**明确不作为证据**——沉默会让用户以为这条没问题
- 报告原话："查过 6 类 15 处，未找到"——这是**证据地图**，不是"你没做"
- 三条纪律：`no_evidence` 永远是"我没找到"；一条 claim 只有一个断言；`contradicted` 必须贴得出反证
- `audit effort` 可计算：类数 = 探测项数，处数 = `sum(scanned)`

引用产物：`gap-engine/reports/fx-spec.md`（"支持 500 并发用户"条目）

## P7 · 核心亮点②：判据外置，翻不出来就拒答（创新性 / 技术实现）

要点：
- 可判定的前提是**判据存在且外置**：声称自带阈值 / 需求文档 / OpenSLO `target` / 事前声明的行业惯例（须标来源）
- 机器已实现：`spec.py` 的 `UNMEASURABLE` 把"高性能 / 高效 / 快速"翻成 **`P95 < 300ms 或 QPS ≥ 500`**，并在报告里标明"默认判据"
- 翻不出来的（"架构合理""美观"）→ **拒绝生成补齐物，标不可判定**，给改写建议
- 这条决定 Healer 的死线：**只补观测、不补实现**；判据没法外置就不许补
- 判据改了要能追责：`CRITERIA.md`（判据出处）+ 原始日志（roadmap 形态）

引用产物：`gap-engine/src/gap_engine/spec.py`；`gap-engine/reports/fx-spec.md`（预检段）

## P8 · 核心亮点③：双方共用的尺子 = 可信度的 CI（创新性）

要点：
- A 查 B 时 B 会防御、数据拿不到；**两人共用一把尺子，争议就变成"看尺子"**
- CI 不保证没 bug，只保证**结果可复现**；我们不保证判得对，只保证**轨迹可核**
- CI 会漏，没人因此不用 CI——**因为它的价值是给所有人一个共同的、可复现的事实**
- 前提是**边界公开**：哪些判不了、说不清率多少、哪类会漏——公开边界的工具错了也在预期内
- 所以 `search_trace` 和"说不清率"不是诚实姿态，**是产品设计**

引用产物：`对账引擎/README.md`（立场节）；`对账引擎/对抗自查.md`

## P9 · 技术实现与工程质量（技术实现 / 工程质量与可复现）

要点：
- **能用规则判的绝不给 LLM**：路由 / 依赖 / 测试文件 / 锁 / 压测产物全走规则，定位率天然接近 100%
- AI 只承担唯一开放的那一步：**"要证明这句话，需要查什么？"**（推演 + 换假设重搜，上限 3 轮）
- 判定域只开 `performance` / `concurrency` / `feature` / `testing`；其余标 `out_of_scope`，不扩类也不硬判
- 可复现：`pip install -e gap-engine` → `gap --help` → 一条命令出报告；测试套件全绿（条数以提交版 `pytest -q` 为准）
- 匿名化：不含 `.env` / API Key / 第三方项目原始代码

引用产物：`gap-engine/tests/`；`readme/install.md`、`readme/run.md`

## P10 · 码道应用说明（**独立页**，码道使用深度 25）

要点：
- **需求分析**：需求清单可判定性预检（哪些要求根本没法验收）用码道对话产出规则，落到 `spec.py`
- **生成**：9 个抽取器（含 `artifact` / `negation`）、三态判定、报告渲染、CLI 子命令按 plan → 契约 → 实现推进，每步有会话记录
- **测试**：闸门式验收（每批改动必须过 `pytest`），失败用例原样回灌给码道定位
- **排错**：报告口径类 bug（如"未覆盖"被渲染成沉默）用码道做差异定位，改完补回归用例
- **留痕**：`codearts_proof/daily/D0–D6` 连续记录 + 截图合集 + git log，**每天归档，不做事后补造**

引用产物：`codearts_proof/`（daily / 截图 / 记录）；`gap-engine/tests/`

## P11 · 指标（技术实现；**数字全部占位**）

要点：
- 样本：5 份老师 / 大创需求清单 × 各 5 条 = **25 条**，对 5 个项目代码；**由需求提出人本人判定**
- 作者认可率 **`N=?`**（目标 ≥70%，分母 = 对 + 错，说不清不计）
- 定位率 **`N=?`**（目标 ≥90%，分母 = 断言型结论）
- 漏报率 **`N=?`**（≤20%，主动报）｜误报率 **`N=?`**（≤10%，主动报）——**两个必须分开报**
- 无法证伪异议率 / 说不清率 / 未覆盖率 **`N=?`**（如实报，不设目标）
- 普遍性（prevalence）：默认取**先验值**（`baseline.PREVALENCE`，标「先验」）；实测为 **`N=?`**（跑过 `tools/measure_prevalence.py` 后填入，标「实测」）——两者不得混用

> **所有 `N=?`：待 5 份需求清单回执后填入，禁止估算。** 一个数字后面必须带 N；有效回执不是 25 就如实写。

引用产物：`对账引擎/施工图-对账引擎.md` §2.6；`gap-engine/reports/`（六份 fixture 报告仅作方法示例，**不是评测样本**）

## P12 · 我们不能证明什么（边界页，主动划线）

要点：
- 这是 **pilot**：25 条结论、有效回执 **`N=?`**（待 5 份需求清单回执后填入，禁止估算）
- 只回答三件事：**方法在真实小样本上跑得起来 / 定位率多高 / 错误长什么样**
- **不做显著性声明**，不宣称普适准确率；限定 Python / JS、500–5000 行、只判四类条目
- 不做"全面理解代码"（CodeWiki 1,862★ 等已占位），只做"这代码在干什么"的报告一段
- 需求清单来源逐份标注；自己反写的不计入样本

引用产物：`对账引擎/日程计划-初赛冲刺.md` §5；`对账引擎/对抗自查.md`

## P13 · 相关工作与差异化（创新性与价值）

要点：
- **简历验证有人做过，全死了**：SkillTruth 4★（退化成 AI 面试）/ labora 2★（退化成简历润色）/ Ada 1★（做太深做不完）
- 死因不是路死了，是**站错了边**：站在"查"的立场 → 被查的人不配合 → 数据拿不到
- 与 DocPrism（98% → 14%）的区别：比的是**项目级声称 vs 整仓证据**，要**先推演该去哪找**，且只报"我没找到证据"
- 与 traceability 工具（doorstop 697★ / duvet 172★）的区别：它们靠**人维护链接**，我们靠搜索找证据并交出轨迹
- 与 schemathesis / Pact 的区别：**行为契约我们不碰**，只做能力契约
