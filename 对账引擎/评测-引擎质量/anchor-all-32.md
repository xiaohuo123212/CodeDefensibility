计算过程（可复算）：
- 确定判断数 = 有证据 + 有反证 = 8 + 0 = 8（「没找到证据」与「不判定」都不算确定判断）
- precision = 判对数 / 确定判断数 = 8 / 8 = 100%（8 条有证据全部判对，`contradicted` 0 条）

- 新库：确定判断数 = 有证据 1 + 有反证 0 = 1，precision = 1/1 = 100%（n=1，不具统计意义）；recall = 判对 1 / 真 supported 12 = 8.3%

## 结论

三态判定在四个真实库上的总体表现：**判对 8/32 = 25.0%，漏报 19/32 = 59.4%，误报 0/32 = 0%，另有 5/32 = 15.6% 被预检挡回不入三态；引擎总共只下了 8 次确定判断，8 次全部正确（precision 8/8 = 100%），但对 32 条真实实现的召回只有 8/32 = 25.0%（可判 27 条口径 8/27 = 29.6%）**。也就是说：敢说的全部说对，但大多数该说的没说——错误全部集中在「漏报」一侧（19 条），误报仍为 0。三个新库（纯 Python 库、无 Web 入口）12 条里只判对 1 条、下过 1 次确定判断、5 条被预检拒答，召回 1/12 = 8.3%，显著差于 filelock（判对 7/20 = 35.0%），说明现有探测项与关键词表是按「有路由、有依赖声明、有启动入口」的应用型仓库设计的。注意新库的 precision 100% 来自 n=1 的确定判断，不能当作能力结论。

## 与新库相关的引擎缺陷（只记录，未修改任何源码/测试/契约）

1. **「安全类」拒答是设计如此，但对安全型库的适配代价很大（不是缺陷）。** itsdangerous 2/5、markupsafe 2/4 被以「安全类需求不在本次判定范围」拒答。该行为由 `contract/scope.md:16,39,48` 明文规定：安全是属性而非事实，仓库里看得到鉴权/校验代码，但机械推不出「所有入口都被覆盖」。因此**不建议改为按措辞放行**——那会让「安全」重新变成不可证伪的判断。真正要记录的是产品后果：对 markupsafe 这种整个库就是「转义/安全」的项目，一半声称无法评测；对外讲四库评测时必须把「5 条不判定」单列，不能混进三态分母。
2. **同一份实现被两种对待，反映的是判定域按措辞触发。** markupsafe 第 1 条（HTML/XML 安全文本对象）因含「安全」被拒答，第 4 条（`Markup` 是 str 子类、自动转义）指向同一份代码却判 `supported`。这在契约上是自洽的（判定对象是声称而非代码），但读报告的人会觉得矛盾。属于表述层问题，可在报告里对「不判定」条目补一句关联说明，不改判定逻辑。
3. **「入口/路由」探测对纯库项目恒为 0（真缺陷）；依赖一栏是措辞问题，不是漏读。** 三个库的报告都写「未识别到启动入口」，`路由/入口` 一类扫描量分别为 15/1、12/1、7/1 处、命中恒为 0。对库型项目应关闭路由探测、改为按模块导出（`__init__.py` 的 `__all__`）建立入口。但「依赖」一栏经核实**不是漏读**：三库的 `pyproject.toml` 都有，只是都没有 `dependencies` 字段（itsdangerous / markupsafe / blinker 都是零运行时依赖），因此「依赖 0 个」是准确的；真正的问题是报告写成「未识别到依赖声明」，读起来像没找到声明文件。这属措辞，改法是把「未识别到依赖声明」与「依赖 0 个」按实际情形区分开。
4. **检索按短语匹配，匹配不到实现标识符。** 典型漏报：①「自定义数据序列化方式」→ 实现名 `serializer` / `serializer_kwargs` / `load_payload`；②「按需压缩数据」→ 实现名 `zlib.compress` + 长度比较（`url_safe.py:58-62`）；③「时间戳自动校验」→ 实现名 `TimestampSigner` / `max_age` / `SignatureExpired`；④「任意数量的订阅者」→ 实现名 `receivers` / `_by_sender`（`defaultdict(set)`）；⑤「特定 sender 或任意 sender」→ 实现名 `ANY` / `ANY_ID` / `receivers_for` 的并集运算。这些不是「代码里没有」，而是「词表里没有」。
5. **跨方法闭环无法拼装。** blinker 的「订阅」语义拆在 `connect`（`base.py:91-139`）与 `receivers_for`（`:326-345`），`send` 体内只看到 `self.receivers_for(sender)` 调用。按单函数/单文件打分时，`send` 单独看既没有「订阅者」也没有「数量」信息，这是第 2、3 条同时漏报的机制性原因。
6. **性能类需求被预检挡回（blinker 1/3）。** 预检把「快速」翻译成「P95 < 300ms 或 QPS ≥ 500」，库里没有基准代码，于是整条不判定。这个拒答本身合理（无基准无法验收），但代价是以性能为卖点的库永远测不到该类声称的检索能力；若要覆盖，需允许「存在分发/调度实现」作为弱证据单独记一档。
