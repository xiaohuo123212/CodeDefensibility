## 1. vibecoding 下如何不塌质量：5 道闸门

大幅 vibecoding 的真实风险不是"写不出来"，是**AI 各自发明字段、编造数字、偷偷新增第四态**。用 5 道闸门把风险挡在合并前。

### G0 契约包（D1 上午冻结，之后只许加不许改字段名）

一个目录 `contract/`，所有 AI 会话的 prompt 都以它开头（复制粘贴，不靠记忆）：

```
contract/
  CONTRACT.md     # 本文件下方"契约十句"
  schema.py       # §1.2 三个 dataclass，字段名钉死
  verdict_table.md # §1.5.1 三态判定表原文
  fixtures/       # 3 个微型仓库（见 G1）
  prompts/        # 每个会话用的 prompt 模板（4 段式）
```

**契约十句（任何 AI 会话都不得违反）：**

1. 字段名只能来自 `schema.py`，不许重命名、不许加别名字段。
2. 状态只有 `supported / contradicted / no_evidence`，**不许新增 `partial`**。
3. `contradicted` 必须带 `file:line`，带不出就降 `no_evidence`。
4. `supported / contradicted` 必须有 `locator`；`no_evidence` 必须有 `search_trace`。
5. `search_trace` 的每一项必须有 `probe / target / scanned / hits / where` 五个键。
6. 报告里所有数字只能由 `len(search_trace)` 和 `sum(scanned)` 算出，**代码里不许出现裸数字**。
7. `performance / concurrency` 只有配置无测量 → `no_evidence`，reason 写"有配置，无测量"。
8. 抽取器只返回证据单元（Evidence），**不许在抽取器里判 status**。
9. LLM 只用于两处：抽声称+分类、推演搜索计划（含换假设）；其它一律规则。
10. 任何"看起来更聪明"的改法，先改 `CONTRACT.md`，再改代码。

### G1 fixture 回归（每次合并必跑，目标 20 秒内）

3 个微型仓库，每个 < 40 行，覆盖一条主路径。**这就是你的回归网**：

| fixture | 构造 | 期望输出（断言） |
|---|---|---|
| `fx-concurrency` | Flask 单进程 + gunicorn workers=4，无压测脚本 | `concurrency` 类 claim → `no_evidence`，`search_trace` ≥3 类，`where` 含 `gunicorn.conf.py` |
| `fx-feature` | 有 `/export` 路由 + openpyxl 依赖 | `feature` 类 claim → `supported`，`locator` 非空 |
| `fx-testing` | 有 3 个 test 文件 + coverage 配置，无覆盖率报告 | `testing` 类 claim → `supported` 或 `no_evidence`（二者之一，但 `search_trace` 必须非空），且**不许崩** |

跑法：`pytest tests/test_fixtures.py -q`。**红灯不许合并。**

### G2 三态判定表 → 表驱动测试

把 §1.5.1 直接翻译成 `pytest.mark.parametrize`，覆盖 9 种情形（有 high 证据 / 2×medium / 1×medium / 只有配置 / 有反证+更强正证 / 有反证无正证 / 空证据 / out_of_scope / coverage=none）。这张表是标注、指标、答辩的共同底座，**AI 改坏它等于改坏整个方法论**。

### G3 可算性断言

`tests/test_report_math.py`：断言报告里渲染的"查过 4 类 11 处"与 `len(trace)/sum(scanned)` 严格一致。
这条专门防 AI 在报告里写漂亮的示例数字。

### G4 人眼抽查（每天 15 分钟）

每天抽 5 条结论，**人指着 `file:line` 去代码里核对一眼**。只审"结论对不对"，不审 AI 写得漂不漂亮。
抽到 1 条明显错 → 当天找根因（通常是判定表被绕过，或抽取器把命中当证据）。

## 5. 指标与答辩口径（初赛版）

| 指标 | 初赛目标 | 说明 |
|---|---|---|
| 作者认可率 | ≥70%（N≈15） | N 小就如实写，PPT 标注"初赛版 N=15，决赛补齐至 50" |
| 定位率 | ≥90% | 分母 = 断言型结论；这是规则抽取器保障的，最容易站住 |
| 漏报率 | ≤20%，**主动报** | 与误报分开，绝不合并成"误报" |
| 误报率 | ≤10%，**主动报** | 同上 |
| 无法证伪异议率 / 说不清率 / 未覆盖率 | 如实报，不设目标 | 主动报边界是加分项不是减分项 |

**PPT 必写的一页（"我们不能证明什么"）：**
> 这是 pilot：**5 份老师/大创需求清单 + 5 个项目代码 / 25 条结论 / 有效回执 N=15**。只能回答"方法在真实小样本上跑得起来、定位率多高、错误长什么样"，不做显著性声明。限定 Python/JS，500–5000 行，只判定四类条目；需求清单来源逐份标注，自己反写的不计入样本。

**交接（`author_verdict` 语义不变）**：提出人（老师 / 项目负责人）只判"系统这条结论对不对"，三个按钮（对/错/说不清）两分钟；item 真假靠 `author_evidence` 是否有出处体现。**不要新增字段。**
