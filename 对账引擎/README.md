# 对账引擎（Gap Engine）

> 一句话：**给一份需求清单（老师 / 大创 / boss 写的）和一个代码仓库，输出「要求做的」和「代码里有的」之间的缺口。**
> 副模式（面试自检，命令是 `gap analyze`）保留原来的用法：给一份"声称"（README / 简历），输出「你说的」和「代码能证明的」之间的缺口。`--claims` 是双模式 roadmap 里的参数名，**当前未实现**。

---

## 立场：不是判官，是双方共用的尺子

**如果 A 查 B，B 会防御、会 argue，数据拿不到。如果两人共用一把尺子，争议就变成"看尺子"。**

| 如果 A 查 B | 如果两人共用一把尺子 |
|---|---|
| B 会防御、会挑刺、会 argue | 争议变成"**看尺子**" |
| 数据拿不到 | 双方都主动跑（都想赢）|
| A 要证明工具准 | **双方一起证明结果可复现** |

最好的类比是 **CI 绿灯**：作者和 reviewer 都看 CI，CI 绿了，reviewer 不再问"你这能跑吗"。**但 CI 会漏**——覆盖不到的地方照样有 bug，没人因此不用 CI。因为 CI 的价值不是"保证没错"，是"给所有人一个共同的、可复现的事实"。

> **我们做的是「可信度的 CI」。**

| | CI | 我们 |
|---|---|---|
| 保证什么 | 不保证没 bug，保证**结果可复现** | 不保证判得对，保证**轨迹可核** |
| 不完美怎么办 | 覆盖率低就补测试 | 说不清就标"说不清" |
| 前提 | **边界公开**（哪些没覆盖） | **边界公开**（哪些判不了、说不清率多少）|

**前提是边界公开。** 不公开边界的工具错一次就死；公开边界的工具错了也在预期内。所以 `search_trace` 和"说不清率"不是诚实姿态，是产品设计。

产品上由此有四个改动：输出**报告**而不是判决书（可复核、可质疑、可重跑）；**双方都能跑**（交差方看"我还差什么"，验收方看"他还差什么"，同一段代码、同一引擎、同一份轨迹）；分歧 = **输入不同**（需求/声称版本不同），工具只负责把输入差异显出来；**主动公开边界**。

## 问题

每个做过项目的人都被问过同一句话：

> "你说这个项目支持 500 并发 —— 怎么证明？"

绝大多数人答不上来。不是因为撒谎，是因为**从来没人告诉他，他的代码缺了哪一块证据**。

这件事在每个场景里重复发生：

| 场景 | 谁在问 | 后果 |
|---|---|---|
| 课程设计 / 大创结题 | 老师 / 评审 | 要求做的没做，或者做了说不清 |
| 团队交接 | 接手的人 | "这模块干嘛的"没人说得清 |
| 外包 / 甲方交付 | 客户 | 需求清单上打了勾，代码里找不到 |
| 面试 | 面试官 | 准备了三个月的项目，三分钟被问穿 |
| 开源项目 | 使用者 | README 说支持 X，实际不支持 |
| 自己的项目 | 自己 | 不知道自己几斤几两 |

而 2025 年之后这件事变了：**AI 让"说自己做到了什么"变得极其廉价**。简历、项目描述、README 都可以一分钟生成一千字。

**声称的生产成本塌了，验证的价值就上来了。我们做的是验证。**

**主场景换成了"交差"**：需求清单的发起人是老师 / boss，不是我自己。所以痛点不是我为什么要给自己找茬，而是**要求做的，我做完了吗，能交差吗**。

## 我们做什么

### 输入

```
一份需求清单（老师 / 大创的课程设计要求，Markdown 列表）  +  一个代码仓库
```

需求清单格式：Markdown 列表，每行一条（`- ` / `* ` / `+ ` / `1. ` / `1) ` / `- [ ] ` 开头），重复行自动去重。

> **来源必须标明**：以老师 / 大创的课程设计要求为主；自己按真实项目反写的清单只作 demo 兜底，**不计入 5 份样本指标**。

副模式（面试自检）：一个代码仓库 + 它自己的 README（或简历里的技术声称）。

### 怎么用

```bash
# 主模式：需求核对（已实现）
gap spec <repo> --spec <requirements.md> [--out reports/<repo>-spec.md]

# 副模式：面试自检，从仓库 README 抽声称（已实现）
gap analyze <repo> [--out reports/report.md]
gap questions <repo> --top 10

# 双模式：同时读需求清单 + 自我声称（未实现，roadmap）
gap analyze <repo> --claims --spec <requirements.md>
```

> `--claims` 是 roadmap 里的参数名。当前 `analyze` 只读仓库 README，**不能**同时读需求清单。

### 输出

```
① 需求可判定性预检          —— 共 N 条 / D 条可判定 / K 条无法验收，逐条给改写建议
② 这个项目实际是什么        —— 由 structure / entry / deps / tests 抽取器读出（规模 / 入口 / 依赖 / 测试）
③ 需求 ↔ 证据 对照表        —— 每条：有证据 / 有反证 / 没找到（并注明覆盖率）
④ 会被追问的问题清单        —— 按"答不上来的可能性"排序；断言带 文件:行，没找到的带搜索轨迹
⑤ 最小补齐行动              —— 补一个脚本？加一个配置？写一段 README？
⑥ 可直接应用的补齐物        —— 生成 + 跑通才给（Healer / Verifier 闭环，roadmap，未实现）
```

报告里的段落顺序就是 `① → ② → 概览 → 逐条 → 未覆盖 → 局限`。

### 一条结论长什么样

```
「支持 500 并发用户」（来源：requirements.md#L12）
  查过 4 类 11 处：
    压测产物    扫描 4 处，命中 0
    并发原语    扫描 3 处，命中 1  app/server.py:34  threaded=True
    worker 配置 扫描 2 处，命中 1  gunicorn.conf.py:3  workers=4
    连接池/限流 扫描 2 处，命中 0
  结论：有并发配置，没有任何测量证据（no_evidence）
  会被问：worker 为什么定 4？压过吗？P95 多少？
  该补什么：一个 locustfile + 一次压测结果（约 30 分钟）
```

**注意"查过 4 类 11 处"这一行。这是产品的良心所在：输出不等于证据，连"没查到"也如实标出来。**

## 怎么工作

```
┌──────────────────────────────────────────────┐
│ ⓪ 适配器层（入站：声称源）                      │  需求清单.md / README.md / 简历.md
│    只做格式翻译，不做判定                       │  OpenSLO.yaml 等属 roadmap
│    中间产物是 Claim schema（★ 这才是资产）      │  标准会变，schema 不会
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ ① 条目层（Item / Claim）                       │  需求清单 / README / 简历 / PR 描述
│    抽出来 → 分类成七类；authority 区分         │  external（别人要求）/ self（自己声称）
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ ①.5 可判定性预检（需求模式才有）                │
│    这条要求能不能被验收？不能 → 给改写建议       │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ ② 推演（Agent 真正干活的地方）                 │
│    为了证明这句话，需要查什么？                  │
│    这是开放问题，每次都不同                     │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ ③ 搜索（观察-思考-行动循环）                    │
│    执行搜索计划 → 命中 → 换假设 → 再搜          │
│    产出：命中项 + 未命中项 + 完整搜索轨迹         │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│ ④ 对账 → supported / contradicted / no_evidence│
│    每条带 文件:行 + 片段 + 置信度               │
└──────────────────────┬───────────────────────┘
                       ↓
        ┌──────────┬──────────┬──────────┬──────────┐
        │ 需求核对  │ 面试自检  │ CI 门禁   │ IDE 悬浮  │
        │ ← 主渠道  │ ← 副渠道  │ ← roadmap │ ← roadmap │
        └──────────┴──────────┴──────────┴──────────┘
```

**出站适配器**：当前只输出 **Markdown 报告 + JSON**（`gap analyze --json`）。SARIF（进 GitHub Code Scanning / DefectDojo）与 OpenSLO 都是 **roadmap**，材料里不许写成已完成。

> **SARIF 为什么推迟**：**语义错位——缺证据 ≠ 缺陷**。SARIF 的语义是"这里有个 bug，去修它"；我们的 `no_evidence` 是"我查过这些地方，没找到证据"。硬塞进 code scanning，等于把"我没找到"说成"你的代码错了"，正是这个产品最不能做的事。

**入站**当前只吃 Markdown 需求清单 / README；OpenSLO.yaml 属 roadmap（**商业方向，非比赛方向**：它的用户是大厂 SRE，不是课程设计 / 大创的真实用户）。

### 为什么 AI 是必需的

不是"给规则套个 LLM 壳"。AI 承担的是**唯一开放的那一步**：

> **"要证明这句话，需要查什么？"**

"支持 500 并发" → 查压测、查锁、查 worker、查连接池（相对固定）
"处理了 10 万条数据" → 查分页？查流式？查批量提交？查数据库索引？（完全不同）

**规则只能覆盖已知类型；面对没见过的声称，必须推演。** 这就是 AI 不可替代的位置。

其它能确定判的（有没有 lock、有没有 test 文件、依赖清单、需求条目能不能验收）**全部用规则**——这样定位率天然接近 100%，预检也能给出同一套建议。

## 和什么不一样

| 已有的东西 | 它在看 | 我们在看 |
|---|---|---|
| CodeQL / Semgrep / ruff | 代码违反了哪条规则 | **需求条目**有没有证据 |
| code review / CodeRabbit / 阿里 open-code-review | 这段代码该不该进主干 | 这份交付**能不能被验收** |
| CodeWiki / DeepWiki / 代码理解 | 这段代码在干什么 | 需求说的和它干的一致吗 |
| AI 模拟面试 | 你的**措辞**像不像那么回事 | 你的**代码**撑不撑得住 |
| 文档一致性检查 | 文档有没有过期 | 需求有没有证据，以及**缺什么** |
| **doorstop / duvet / ASSERT**（requirements traceability） | **人工**把需求链接到测试用例、出合规报告 | **AI 自己去找证据**，给搜索轨迹；人不用维护链接表 |
| 需求质量检查（acceptance criteria checker） | 需求写得对不对（多为 0★ 试验品） | 需求**能不能验收** + 代码**做了没有**，同一条流水线 |

**一句话差异：traceability 工具靠人维护链接，我们靠搜索找证据；其它工具都在看代码，我们看"代码和要求的距离"。**

## 契约二分：红海在哪，我们站哪

**契约必须切两半，我们只碰后一半。**

| | **行为契约**（受保护） | **能力契约**（我们的） |
|---|---|---|
| 说什么 | 路径存在、参数类型、响应 schema、状态码 | **P95 < 300ms、可用性 99.9%、支持 500 并发** |
| 标准 | **OpenAPI / Pact / AsyncAPI**（成熟） | **OpenSLO**（有规范，**无验证工具**） |
| 工具层 | schemathesis **3,777★**；pact-ruby 2,196★ / pact-jvm 1,148★ / pact-net 934★ / pact-python 689★；spring-cloud-contract 728★ | sloth 2,572★（生成）、OpenSLO 规范 1,542★、oslo 222★（CLI）、**验证类：0** |
| 我们 | ❌ **绝对不碰** | ✅ **这才是我们的地方** |

**"接口符不符合 OpenAPI"，schemathesis 一个命令就干完，比我们准。** 那是行为陈述——一条规则能判的那一半。

**凡是"一条证据就能判"的，都不是我们的活。凡是"需要一组证据、而且不知道该找哪一组"的，都是我们的活。** 这句话在代码里已经落地：分类器认七类，判定域只开 `performance` / `concurrency` / `feature` / `testing` 四类（`schema.py` 的 `JUDGEABLE_TYPES` + `pipeline.py` 的 `is_judgeable`），其余三类标 `out_of_scope`，报告写"本工具不判定该类型"。

**能力契约的判据必须外置。** 声称没带阈值时，用 `spec.py` 里的默认判据并把来源写出来（例：`高性能` → `P95 < 300ms 或 QPS ≥ 500`）；判据不可外置的（如"架构合理"）直接拒绝生成，标"不可判定"。

## 现在的状态

- **2 人 / 初赛 6 天（D0–D6，11-15 → 11-20 15:59:59 提交）**；"2 周 / 14 天"口径已作废，只能用于描述**决赛期**，初赛材料不得引用
- 主渠道：**需求核对报告**（`gap spec`，CLI + 极简页面）
- 副渠道：**面试自检**（`gap analyze` / `gap questions`，复用同一引擎）
- Agent 口径（对外统一）：**7 个 Agent 位 = 5 个已实现（Claimer / Prober / Matcher / Challenger（规则版）/ Renderer）+ 2 个 roadmap（Healer / Verifier）**；**`baseline` 先验是 Matcher 的内部机制，不占 Agent 位**
- roadmap（**架构已支持，未实现**）：**双模式（`--claims --spec` 同时读）**、Healer / Verifier 生成闭环、CI 门禁、IDE 悬浮、**SARIF 出站**（`~1 天`，理由见上：语义错位，缺证据 ≠ 缺陷）、**OpenSLO 入站**（商业方向，非比赛方向）、**`gap explain <问题>`**（**需要调用图，不是现有索引的副产物**）
- 第三类用户：**接手的人**（"这代码在干什么"）——不是新功能，是对账的副产物，报告 ②「这个项目实际是什么」就是它；`gap explain` 是它的 roadmap 出口
- 工期纪律：**能以规则判的，绝不给 LLM；能少做的渠道，绝不在 6 天里加**

**已实现**（可跑、有测试）：

- `gap spec <repo> --spec <requirements.md>`：需求清单解析 → 可判定性预检 → 逐条对账 → 报告
- `gap analyze <repo>`：从仓库 README 抽声称 → 逐条对账 → 报告
- `gap questions <repo> --top N`：按 `question_priority` 输出追问清单
- 数据模型含 `authority`（`external` / `self`）；`Verdict.rounds` 是真实字段（实际跑过的检索轮数，不是硬编码 `1`）
- 报告含 `## 需求可判定性预检` 与 `## 项目实际是什么` 两段
- **多轮换假设检索**（`prober.ALTERNATE_PLANS` + `pipeline` 挑战循环）：`performance` / `concurrency` 第 2 轮加查「压测结果文件」，`testing` 第 2 轮加查「覆盖率产物」；只升不降、证据与轨迹累加、`max_rounds` 钳制 1..3，**只有 `no_evidence` 进第 2 轮**（`supported` / `contradicted` 第 1 轮即返回），报告逐条段出现 `换假设：N 轮（第 1 轮查预设来源，其后换假设重搜）`
- **`Challenger`（规则版）**：即上面这条换假设重搜——**不做 LLM 反证、不做多 Agent 对话**；产物证据见 `gap-engine/reports/fx-challenge.md`
- **`contradicted` 三态产出**：只认显式否定声明（`extractors/negation.py`）、必须与需求关键词相关、必须能贴 `file:line`（贴不出降回 `no_evidence`）；反证优先于支持证据，被推翻的支持痕迹条数写进 `reason`；第 1 轮即定论、不进挑战循环。产物证据：`gap-engine/reports/fx-contradicted.md`（`结论：代码里有反证，与要求不一致`、`- 定位：app.py:9`）

**未实现**（roadmap，材料里不许写成已完成）：

- `--claims --spec` 双模式（"我吹的" vs "我要做的"是不是一回事）
- Healer / Verifier：生成补齐物并跑通（**只补观测、不补实现**；补齐物 = `locustfile.py` + `CRITERIA.md` + `run.sh` + 原始日志）

- CI 门禁、IDE 悬浮
- **SARIF 出站**（推迟理由：语义错位，缺证据 ≠ 缺陷）、**OpenSLO 入站**（商业方向，非比赛方向）
- **`gap explain <问题>`**（需要调用图，不是现有索引的副产物）

- 判定域：**识别七类条目，只对 performance / concurrency / feature / testing 四类下结论**；其余标"不判定"
- 评测：**5 份老师 / 大创的需求清单 × 各 5 条 = 25 条，对 5 个项目代码，由 5 位需求提出人本人判定**（不是我们自己标）；来源在报告和材料里标明，自己反写的清单不计入样本
- 每条结论都输出：**断言给 文件:行，搜索给轨迹，什么都没查到的标"未覆盖"**（`coverage`）。输出不等于证据；漏报率与误报率分开主动报
- 合规：邀请老师 / 项目负责人时取得"仅用于本次评测、匿名、可撤回"的授权；上传前做密钥/隐私扫描，报告不附带原始代码
- 技术栈：Python + tree-sitter + 一个 LLM（DeepSeek-V4.1-Flash 错峰最省）
- 开发工具：华为云码道（CodeArts），全流程留痕
