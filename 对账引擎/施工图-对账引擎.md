## 0. 一句话

> **输入一份需求清单（老师 / 大创 / 客户写的验收要求）+ 一个代码仓库，输出「要求做的」和「代码里有的」之间的缺口。**
> 数量：初赛 **25 条**（5 份清单 × 各 5 条，对 5 个项目代码）；决赛 50 条。副模式也接受一份自我声称（README / 简历）。
> 每条缺口给：定位（能定位时）+ 搜索轨迹（查过哪里）+ 该补什么；查不到的标"未覆盖"，不沉默。

**核心概念：可辩护性（defensibility）。** 你的代码能不能支撑**别人的要求**。

**立场：不是判官，是双方共用的尺子——「可信度的 CI」。** 交差方看"我还差什么"，验收方看"他还差什么"；同一段代码、同一引擎、同一份轨迹。CI 不保证没 bug，只保证结果可复现；我们不保证判得对，只保证轨迹可核。前提是**边界公开**。

四个渠道共用这一个引擎：

```
声称层（简历 / README / PR 描述 / 项目文档）
        ↓
【入站适配器】Markdown → Claim schema（OpenSLO 等 roadmap）
        ↓
证据层（代码 / 测试 / 配置 / 依赖 / 注释）
        ↓
对账引擎 ← 唯一要写的东西
  ① supported      有证据
  ② contradicted   有反证（慎用）
  ③ no_evidence    没找到证据
        ↓
【出站适配器】Markdown 报告 + JSON（SARIF / OpenSLO 均为 roadmap）
        ↓
┌──────────┬──────────┬──────────┬──────────┐
│ 体检报告  │ 面试拷问  │ CI 门禁   │ IDE 悬浮  │
│ ← 初赛做  │ ← 顺手    │ ← roadmap │ ← roadmap │
└──────────┴──────────┴──────────┴──────────┘
```

# 一、引擎接口设计

## 1.1 命令行（先定这个，它是你和队友的分界线）

```bash
# 需求核对（主渠道，已实现）
gap spec <repo> --spec <requirements.md> [--out reports/<repo>-spec.md]

# 面试自检（副渠道，复用同一引擎，已实现；声称从仓库 README 抽）
gap analyze <repo> --out report.md
gap questions <repo> --top 10

# 双模式：需求清单 + 自我声称一起读（未实现，roadmap）
gap analyze <repo> --claims --spec <requirements.md>

# 解释"这代码在干什么"（未实现，roadmap）
gap explain <问题> --repo <repo>
```

> **`gap explain` 为什么是 roadmap**：它**需要调用图，不是现有索引的副产物**。报告 §「项目实际是什么」（一句话 + 核心路由）不依赖调用图，初赛就能出；"问题 → 相关代码路径"的那一版要等调用图。

> **已实现 / 未实现要分清**：上面的 `--claims` 是 roadmap 里的参数名，当前 `analyze` 固定读仓库 README，不能同时读需求清单。
> 需求版入口落在子命令 `gap spec` 上，`--spec` 必填；需求清单格式为 Markdown 列表（`- ` / `* ` / `1. ` / `1) ` / `- [ ] ` 开头），重复行去重。
> 双模式的价值（能抓出"需求写着要做 A，README 吹的是 B"）先写在材料里，代码留到决赛期。

**`gap questions --top` 的排序键（先定死，别临场拍）：**

```
question_priority = 状态权重 + 缺口权重
  状态权重：no_evidence=3，contradicted=2，supported=1
  缺口权重：confidence=low=3，medium=2，high=1
  同分按 claim_id 稳定排序（保证可复现）
```

报告里必须显示每条问题的分值与依据，否则"按答不上来的可能性排序"无法自证。

## 1.2 数据模型（两人 D1 就要对齐，之后不许改字段名）

```jsonc
// 一条"待验证条目"（需求条目或自我声称）
{
  "id": "c1",
  "text": "支持 500 并发用户",
  "source": "requirements.md#L12",    // 出处必须可定位
  "authority": "external",           // external（别人要求：需求清单）| self（自己声称：README/简历）
  "type": "concurrency",             // 见 1.3
  "checkable": true,                 // 能不能用代码验证
  "uncheckable_reason": null,        // checkable=false 时写原因（如"需要线上数据"、"需求本身不可判定"）
  "out_of_scope": false              // 落在判定域之外（见 1.3：识别七类，只判四类）
}

// 一条"证据"
{
  "id": "e1",
  "kind": "code",                    // code|test|config|dep|comment|bench
  "file": "app/server.py",
  "line": 34,
  "snippet": "app.run(threaded=True, processes=1)",
  "supports": ["concurrency"],       // 写 type，不写 claim id；claim 映射在 Matcher 阶段完成
  "strength": "medium"               // high|medium|low；不用 0-1 小数，50 条样本校准不了概率
}

// 一条"对账结论"（每一类都输出，包括"什么都没查到"）
{
  "claim_id": "c1",
  "status": "no_evidence",           // supported | contradicted | no_evidence（判定见 §1.5.1）
  "confidence": "medium",            // high|medium|low

  // 输出 ≠ 证据：
  //   断言型（supported/contradicted）必须有 file:line
  //   搜索型（no_evidence）可以没有行号，但要给 search_trace
  //   什么都没查到的也照样输出，标 coverage=none，明确"不作为证据"
  "locator": null,
  "coverage": "partial",             // full|partial|none：这条结论的信息完备度
  "evidence_ids": ["e1"],
  "reason": "有并发配置，无测量证据（单进程 Flask 启动）",

  // 报告里原样展示，这是产品的最后一道防线
  // scanned = 该类实际扫描的文件/位置数；hits = 命中数；where = 命中位置
  "search_trace": [
    {"probe": "bench",       "target": "locustfile/k6/ab/benchmark", "scanned": 4, "hits": 0, "where": []},
    {"probe": "concurrency", "target": "lock/thread/async/pool",     "scanned": 3, "hits": 1, "where": ["app/server.py:34"]},
    {"probe": "config",      "target": "worker / pool 参数",         "scanned": 2, "hits": 1, "where": ["gunicorn.conf.py:3"]},
    {"probe": "pool",        "target": "连接池 / 限流",               "scanned": 2, "hits": 0, "where": []}
  ],
  "rounds": 2,                       // 搜索轮数（换过几次假设）

  "question": "你说 500 并发，压测脚本在哪？用什么压的？P95 延迟多少？",  // 面试渠道用
  "question_priority": 8,            // 0-10，越大越先问；排序键见 §1.1
  "fix": "补一个 locustfile.py + 一次压测结果贴进 README（约 30 分钟）"   // 体检渠道用
}
```

> **"查了 4 类 11 处"是可计算的，不是话术：** 类数 = `len(search_trace)`，处数 = `sum(scanned)`，命中数 = `sum(hits)`。上例即 4 类 / 11 处 / 2 命中。**所有对外数字必须能由该结构算出。**

> **输出不等于证据，结论不允许沉默。**
> - `coverage=full`：有断言 + 定位，或搜索完整覆盖；
> - `coverage=partial`：查了，但有明显盲区；
> - `coverage=none`：连像样的搜索都没跑成，或该类型不在判定域。
>
> **`coverage=none` 的结论照样输出**，`reason` 写"未执行有效搜索/无法定位"，报告渲染成"未覆盖"。它**不算证据、不计入定位率，但必须出现**——沉默会让用户误以为这条没问题。
> 说"我没查到"永远比不说安全；这是"判错毁信任"的唯一对冲手段，也是答辩最后一道防线（见 [对抗自查](对抗自查.md) §六）。

## 1.3 声称的七个类型（识别七类，只判四类）

| type | 例子 | 主要证据域 | 是否判定 |
|---|---|---|---|
| `performance` | "QPS 3000"、"响应 <300ms" | benchmark 文件、缓存、索引、连接池 | **是** |
| `concurrency` | "支持 500 并发" | lock / async / thread / worker / pool | **是** |
| `architecture` | "微服务架构"、"分了三层" | 目录结构、模块边界、docker-compose | 否（`out_of_scope`） |
| `feature` | "支持 Excel 导出"、"集成了支付" | 路由、函数、依赖 | **是** |
| `scale` | "处理了 10 万条数据" | 分页、批处理、流式、数据库配置 | 否（`out_of_scope`） |
| `testing` | "测试覆盖率 80%" | test 文件、coverage 配置、CI | **是** |
| `security` | "做了 JWT 鉴权"、"防了 SQL 注入" | 中间件、参数化查询、依赖 | 否（`out_of_scope`） |

> **纪律：识别七类，只判四类。** 分类器必须认识七类，否则 architecture/security/scale 会被误分进 feature，污染样本；
> 但**判定域只有 `performance` / `concurrency` / `feature` / `testing` 四类**，其余三类标 `out_of_scope=true`，报告写"本工具不判定该类型"，不进 25 条分母（决赛 50 条）。
> 出现第八类同样标 `out_of_scope`，别扩类，也别硬判。

## 1.4 证据抽取器（七个，各自独立可测）

| # | 抽取器 | 抽什么 | 怎么实现 |
|---|---|---|---|
| 1 | `deps` | requirements.txt / package.json / go.mod | 解析，输出依赖集 |
| 2 | `entry` | 路由、main、启动命令 | 正则 + AST（tree-sitter 或 Python ast） |
| 3 | `concurrency` | lock/async/thread/worker/pool 相关行 | 关键词 + AST 节点 |
| 4 | `tests` | 测试文件、测试函数数、coverage 配置 | 文件匹配 + 计数 |
| 5 | `bench` | locust/k6/ab/benchmark/timeit | 文件名 + 内容 |
| 6 | `config` | .env / Dockerfile / CI / 连接池参数 | 文件存在 + 关键字段 |
| 7 | `structure` | LOC、文件数、目录层级、单文件最大行数 | 纯统计 |

**关键原则：能用规则判的，绝不给 LLM。**

- "有没有压测脚本"→ 文件搜索，**确定性**
- "有没有锁"→ AST 匹配，**确定性**
- 只有"这句话到底在说什么"才给 LLM

**覆盖等级（决定 25 条样本怎么抽；决赛 50 条同理）：**

| 声称类型 | 主要抽取器 | 覆盖 | 判定 |
|---|---|---|---|
| `performance` | bench + config + entry | 稳定 | 是 |
| `concurrency` | concurrency + config + bench | 稳定 | 是 |
| `feature` | entry + deps | 稳定 | 是 |
| `testing` | tests + config | 稳定 | 是 |
| `architecture` | structure + config | 部分 | 否（`out_of_scope`） |
| `scale` | config + structure | 弱 | 否（`out_of_scope`） |
| `security` | entry + deps | 弱 | 否（`out_of_scope`） |

> **样本抽样规则：每个项目 5 条，全部来自 4 个判定类**（建议 2 performance/concurrency + 2 feature/testing + 1 任意判定类）。弱类声称只记录、不判定，避免用弱抽取器去拉低指标。

这样**断言型结论的定位率由规则抽取器保障**（目标 ≥90%，不承诺 100%）：定位来自抽取器输出，不是模型编的。

## 1.5 对账流程：搜索循环，不是规则匹配

**这是整个设计里最容易被做错的地方。** 如果写成"跑一遍规则 → 匹配 → 出结论"，那它就是 lint 加个 LLM 壳（见 [对抗自查](对抗自查.md) §①）。

**Agent 的位置在"推演要查什么"和"换假设再搜"，不在"判定"。**

```
声称「支持 500 并发」
        ↓
【推演】要证明它，需要查什么？          ← LLM 干这个（开放问题）
        ↓
搜索计划：
  [1] 压测产物：locustfile / k6 / ab / benchmark / 结果 csv
  [2] 并发原语：lock / thread pool / async / worker
  [3] 部署配置：gunicorn workers / uvicorn / nginx
  [4] 连接池 / 限流
        ↓
【执行】逐项跑（规则 + grep + AST，确定性）  ← Prober 干这个
        ↓
命中 [2][3] + 未命中 [1] → no_evidence（reason 写"有配置，无测量"）
未命中 [1]                → 关键缺口（仍输出，coverage=partial）
        ↓
【换假设，再搜一轮】                   ← LLM 干这个
  "也许压测结果写在 README / docs / 博客链接里？"
  → 换关键词再搜（记录在 rounds 里）
        ↓
仍无 → no_evidence
        ↓
输出：三态 + 定位或搜索轨迹 + **coverage** + question + fix
```

**为什么要多轮**：一轮搜索只能覆盖预设的抽出来源，而"证据可能在哪"本身是开放问题。换一次假设再搜一轮，能把漏报率显著压下去。

**上限 3 轮。** 超过 3 轮收益递减且烧积分，写死。

### 1.5.1 三态判定（Matcher 必须按表，不许自创第四态）

| status | 充分条件 | 硬约束 |
|---|---|---|
| `supported` | 至少 1 条 `strength=high` 的直接证据，或 ≥2 条独立 `medium` 证据覆盖同一断言 | 断言型必须 `file:line` |
| `contradicted` | 存在明确反证且能贴 `file:line`，且无更强正证 | 贴不出反证一律降为 `no_evidence` |
| `no_evidence` | 其余全部情形，包括"有配置但无测量" | 输出，不沉默；`coverage` 标清 |

**能力型声称（`performance` / `concurrency`）必须有测量证据才算 `supported`。** 只有配置、依赖或注释、没有压测/基准结果时，一律 `no_evidence`，`reason` 写"有配置，无测量"。

**声称没带阈值时的默认判据（外置、必须写出处）**：`高性能` / `高效` / `快速` → **`P95 < 300ms 或 QPS ≥ 500`**（与 `spec.py` 的 `UNMEASURABLE` 一致，报告里标"默认判据，非声称自带"）。判据不可外置的（如"架构合理"）不许补生成，标"不可判定"。**对外所有材料只许引用 `P95 < 300ms` 这一口径，不许再出现别的并发判据数字。**

> **"部分支持"不是状态，是 `no_evidence` 的 `reason` 措辞。** 例："有并发配置，无测量证据" → `status=no_evidence`。
> **不许新增 `partial` 状态**：三态是标注表、指标和答辩的共同底座，加第四态会让 25 条指标无法对齐（决赛 50 条同理）。

### 三条纪律

| 纪律 | 说明 |
|---|---|
| **`contradicted` 只在能贴出明确反证时用** | 声称"用了 JWT"，代码里是明文密码 + 无 token 逻辑 → 可以。其余一律 `no_evidence` |
| **结论必须输出，信息完备度必须标出来** | 没有轨迹也输出，标 `coverage=none` 并写"未执行有效搜索"；不许用沉默代替结论 |
| **`no_evidence` 的措辞永远是"我找过这些地方，没找到"** | 不是"你没有"。这条纪律就是你的信誉 |

> **"我查了 4 类 11 处都没找到"** 比 **"没找到"** 有力十倍。前者是证据地图，后者是空白。

## 1.6 Agent：7 个 Agent 位，5 个已实现 + 2 个 roadmap

> **对外口径只有这一句**：**7 个 Agent 位：5 个已实现（Claimer / Prober / Matcher / Challenger（规则版）/ Renderer）+ 2 个 roadmap（Healer / Verifier）；`baseline` 先验是 Matcher 的内部机制，不占 Agent 位。**

| Agent | 状态 | 职责 | 为什么必须是独立 agent |
|---|---|---|---|
| **Claimer** | 已实现 | 从需求清单 / README 抽声称 + 分类 | 输入是自然语言，纯语义 |
| **Prober** | 已实现 | 跑八个抽取器，产出证据单元 | 纯规则，不调模型 |
| **Matcher** | 已实现 | 对账，出三态 + 置信度 | 核心推理 |
| **Renderer** | 已实现 | 出报告 / 出问题清单 | 与引擎解耦，支持多渠道 |
| **Challenger** | **已实现（规则版）** | **检索层换假设重搜**：`performance` / `concurrency` 第 2 轮改查「压测结果文件」，`testing` 第 2 轮改查「覆盖率产物」；能落 `file:line` 才升 | **这是最值钱的**：它自己打自己，降漏报 |
| **Healer** | **roadmap** | 补观测（**不补实现**）：生成可复核包并跑通 | 生成物必须可复核，否则"自己出题自己答" |
| **Verifier** | **roadmap** | 专审生成物有没有作弊（并发数、压的接口、判据是否自判） | 复核必须独立于生成 |

> `baseline`（同类项目普遍性先验，双条件缺口的第二条件）**是 Matcher 的内部机制，不占 Agent 位**，材料里不许把它列为已实现 Agent。

> Challenger 的设计参考了 SetupX 的 Prosecutor–Judge 和 Assigner 的对抗验证思路。**答辩时讲这个，评委会觉得你懂"让 AI 检查 AI"这件事。**

> **Challenger 已实现的部分与边界（材料里不许拔高）**：已实现的是**检索层换假设重搜**——`performance` / `concurrency` 第 2 轮改查「压测结果文件」（`artifact` 抽取器），`testing` 第 2 轮改查「覆盖率产物」，新证据能落到 `file:line` 才把结论升为 `supported`（报告逐条段多一行 `换假设：N 轮（第 1 轮查预设来源，其后换假设重搜）`，`N = Verdict.rounds`，即实际跑过的轮数）。**不做 LLM 反证、不做多 Agent 对话**：策略是表驱动的、有限可枚举（`ALTERNATE_PLANS`，每类至多 1 个备用假设，`max_rounds` 钳制 `1..3`），同一仓库两次跑给出同一条 `search_trace`，否则轨迹就不可复核。只对 `performance` / `concurrency` / `testing` 三类定义第 2 轮，其余类型总轮数恒为 1。
>
> **产物证据**：`gap-engine/reports/fx-challenge.md` —— `换假设：2 轮（第 1 轮查预设来源，其后换假设重搜）`、定位 `loadtest/report.log:2`、结论由第 1 轮 `no_evidence` 升为 `supported`。

**Challenger 与 Matcher 冲突的裁决规则（规则版已落地，下列为已实现约束）：**

- Challenger 只能把 `no_evidence` **升级**为 `supported`（它找到了新证据），升级时必须给出 `file:line`；第 2 轮的新证据落不到 `file:line` 就不升；
- 它**不能直接把 `supported` 降级**（实现为：第 1 轮已 `supported` 的条目直接返回、不进循环）；认为误报时提交"反证包"给 Matcher 复核，复核仍坚持则保留，并在报告标"存在争议"（**这一半仍是 roadmap**）；
- 裁决只看一件事：**证据能不能落到 `file:line`**。能 → 升级；不能 → 维持 `no_evidence`。
- Challenger 介入点在"换假设再搜"之后、输出之前；规则版已落地，报告逐条段直接给出 `换假设：N 轮`。**未实现的是 LLM 反证 / 多 Agent 对话那一层**，答辩时按"下一步"讲，不许说成已完成。

---

## 1.7 Adapter 层（**概念性**，初赛不开新工期）

**我们不做标准，做标准之间的翻译层。** 中间那个 `Claim schema` 是我们自己的——标准会变，schema 不会。

```
入站适配器（声称源）              自有内核              出站适配器（渲染）
─────────────────           ──────────────        ─────────────────
需求清单.md      ┐                                 ├→ Markdown 报告（已实现）
README.md       │                                 ├→ JSON（已实现，analyze --json）
简历.md          ├──→  Claim schema  ──→  引擎  ──→ ├→ SARIF（roadmap）
Jira/Linear     │      （★ 这才是资产）            └→ OpenSLO（roadmap，商业方向）
OpenSLO.yaml    ┘
```

| 方向 | 初赛做什么 | 不做什么 |
|---|---|---|
| **入站** | Markdown 需求清单（主场景本来就要）+ 仓库 README | OpenSLO.yaml（用户是大厂 SRE，不是老师 / 大创）、Jira（要 OAuth 和真实 workspace）、简历解析（副渠道用 README 已够） |
| **出站** | **Markdown 报告 + JSON** | **SARIF**、OpenSLO 回写 |

**SARIF 为什么推迟（必须能背出理由）**：**语义错位——缺证据 ≠ 缺陷**。SARIF 说的是"这里有个缺陷，去修"；我们的 `no_evidence` 说的是"我查过这些地方，没找到证据"。硬塞进 GitHub Code Scanning 会把"我没找到"改成"你的代码错了"，正好违背纪律一。**技术上 ~1 天，语义上要先解决。**

**明确不碰**：OpenAPI / Pact 行为校验（红海，schemathesis 更准）、OpenSLO 验证（商业方向，非比赛方向）。适配器层是**架构解释**，不是 6 天里的开发任务——**初赛只做已验证的一进一出（Markdown 进、Markdown+JSON 出），不许用适配器当理由加功能。**

# 二、标注规范（**需求提出人标注版**；初赛 25 条 / 决赛 50 条）

> ⚠️ **本节于 2026-11-14 改版。原方案是"我们自己标 + 交叉复核"，那是循环论证，已作废。**
> **现在由需求提出人标**（老师 / 项目负责人，需求清单的作者）；`--claims` 副模式的样本仍由项目作者本人标。下文"作者"一律按这个定义读。理由见 2.0。

## 2.0 为什么必须让作者标

自己标 ground truth、再用它评估自己的系统，等于自己出题自己考试。评审会（正确地）指出这是循环论证——**这一条不改，整个方法论站不住。**

**让需求提出人（老师 / 项目负责人）判定**，三个好处一次拿到：

| 好处 | 说明 |
|---|---|
| **ground truth 变客观** | 最权威的裁判不是我，是**提要求那个人** |
| **拿到真实用户** | 赛题明确"真实用户验证"是加分项；老师 / 项目负责人就是真实用户 |
| **拿到用户证言** | 答辩素材（"某位老师看完第 3 条结论后说：这条我真没核过"）|

**代价**：要跟 5 位提出人沟通（决赛版 10 位），而且一定有人拖。**所以 D0 就发出去，D5 冻结前收回来。收不回来的清单算作废，换人。**

## 2.1 为什么是 25 条（决赛 50 条）

- 决赛：10 个项目 × 5 条；初赛：**5 份老师 / 大创需求清单 × 各 5 条 = 25 条**，对 5 个项目代码
- 少了算不出率，多了 2 人标不完
- **按 `item` 标注，不按 repo 标注**——因为评测单位是 `item`（一条需求条目，或一条自我声称）

## 2.2 选项目的规矩

| 要求 | 说明 |
|---|---|
| **需求清单来源** | **老师 / 大创的课程设计要求**（必须标明来源）；自己按真实项目反写的只作 demo 兜底，**不进 5 份样本** |
| 代码来源 | 同学的课程设计 / 大创 / 毕设（**匿名**，去掉姓名学号） |
| 规模 | **500–5000 行**（太大标不完，太小没话说） |
| 语言 | **Python 或 JS**（只这两种） |
| 多样性 | 初赛 5 个项目：至少 3 个 Web 后端、2 个数据处理 / 脚本工具；决赛版扩到 10 个项目 |
| **必须有 README** | 否则抽不出副模式的自我声称（需求模式下不是硬门槛） |
| **必须有授权** | 邀请时附"仅用于本次评测、匿名、可撤回"；上传前做密钥/隐私扫描 |

## 2.3 标注表怎么设计（给作者填的必须极简）

**作者不是标注员。** 让他每条填一长串字段，一定没人填。所以拆成两半：

**系统自动产出（提出人看，不改）：**

| 字段 | 来源 |
|---|---|
| `item` | 需求条目（`authority=external`，来自需求清单）或 README / 简历声称（`authority=self`）|
| `type` | 七类分类 |
| `status` | 三态结论 |
| `search_trace` | 搜索轨迹（**给作者看的核心材料**）|
| `locator` | 文件:行 |

**作者只回填三个必填 + 一个可选：**

| 字段 | 取值 | 说明 |
|---|---|---|
| `author_verdict` | **对 / 错 / 说不清** | 判**"系统这条结论对不对"**（不是判 claim 本身真假），就一个字 |
| `author_evidence` | `file:line` 或留空 | **可选**。他觉得代码里其实有证据，就贴位置 |
| `author_note` | 一句话，可选 | "我压测过但没提交" 这类，最有价值的证言就在这 |
| `author_stuck` | 是 / 否 / 未问 | 可选。这道追问你会不会答不上来？用于算"问中率" |

**先钉死 `author_verdict` 的对象：它只回答"系统这条结论对不对"，不回答"这句 claim 是否为真"。** claim 真假由 `author_evidence` 体现——作者贴了出处=这句确实有证据；没贴=他也拿不出。

**由此分出两类方向相反的错误，不再用一个"误报"统称：**

| 情形 | 归类 | 含义 |
|---|---|---|
| 系统 `no_evidence`（说没找到）+ `author_verdict = 错` + `author_evidence` 非空 | **漏报（假阴性）** | 系统漏掉了真实存在的证据 |
| 系统 `supported` / `contradicted`（给出了断言）+ `author_verdict = 错` | **误报（假阳性）** | 系统给出了不成立的结论 |
| 系统 `no_evidence` + `author_verdict = 错` + `author_evidence` 留空 | **无法证伪的异议** | 作者说系统错，但拿不出证据；**单独统计、如实报**，不计入漏报也不计入误报 |

> **不要再用"误报"统称两种错误。** 说漏报就说漏报，说误报就说误报。混用会被评委当场纠正。

**发给作者的话术（照抄）：**
> "我做了个工具，用你的项目试了一下。它说你这几句话说不到底。你帮我看看它是不是瞎说的——每条点一下'对 / 错 / 说不清'就行，两分钟。**尤其如果它说错了，一定告诉我哪错了。**"

**注意最后一句话。** 主动邀请他挑错，否则他会礼貌性地说"都对"——那样你的数据全是废的。

## 2.4 三条纪律（给开发者，也写进报告首页）

**纪律一：`no_evidence` 不是"他没有"，是"我没找到"。**
所有措辞一律"查过 X 处，未找到"，不说"你没做"。

**纪律二：一条 claim 只有一个断言。**
- ❌ "支持高并发、低延迟、高可用"（三个断言）
- ✅ 拆成三条

**纪律三：`contradicted` 必须能贴出反证代码。**
贴不出来就不许标 `contradicted`，一律 `no_evidence`。

## 2.5 作者标注的流程（2 人怎么执行）

**初赛（D0–D6，完整版见 [日程计划-初赛冲刺.md](日程计划-初赛冲刺.md)）：**

```
D0  发出邀约（5 份老师 / 大创需求清单 + 5 个项目代码），说明"两分钟，点三下"；需求清单必须标来源
D1  抽 1 份清单 ≥5 条，系统跑通端到端
D2  清单 × 项目 → 带搜索轨迹的报告
D3  发前 3 位需求提出人 + 需求访谈累计 ≥4（B 端红灯：问不出"哪条要求最难验收"→ 退回 `--claims` 副模式）
D4  5 份清单 × 5 个项目全跑 → 25 条结论 + 指标带 N
D5  冻结 freeze-v1，冻结版对 5 个项目整体重跑
D6  11-20 15:59:59 提交
```

**决赛版（D7–D9，见 §三）：** 补到 10 份清单 / 50 条 → 收齐回执 → D9 冻结版重跑并分析漏报/误报。

**分歧怎么处理**：需求提出人与系统不一致时，**以需求提出人 verdict 为准记录分歧**（除非他本人也说不清）。**不要跟他争。** 记录分歧不等于计入错误率：按 §2.3 的三行口径，只有"能贴出出处"的才进漏报/误报；**"无法证伪的异议"只记录、通报，不表述为"系统错"，也不进任何错误率**。**需求提出人说了算的是"结论对错"，证据有无看他能不能贴出位置。**

`author_verdict = 说不清` 单独统计——这类最有价值，因为"连提出人自己都说不清这条要求算不算有证据"，恰恰证明"可辩护性"有模糊区。

> 答辩时用得上："这 6 条需求提出人自己也说不清，说明'可辩护性'不是非黑即白的。"

## 2.6 从标注算出的数字（这就是你的 PPT）

**评测口径（三条硬约定，先钉死）：**

1. **版本冻结**：初赛 **D5（11-19）** 为代码冻结日，冻结版本对 **5 个项目**（5 份清单 × 各 5 条 = 25 条）整体重跑，报告首页写 `commit hash + 日期`；D1–D3 的回执只作过程反馈。冻结后只许改文案和渲染，**不许再改判定规则**。**决赛版口径**：D9 冻结、10 个项目 / 50 条整体重跑。
2. **分母**：所有比率的分母 = **收到有效回执的 claim 数**。未回执、`out_of_scope`、`coverage=none` 的结论**单列，不进分母**。
3. **N 必须写出来**：每个比率后面标注实际 N（如"认可率 72%（N=15）"）。初赛 N 不是 25 就如实写，决赛版不是 50 就如实写，不硬凑。

| 指标 | 定义 | 分母 | 目标 |
|---|---|---|---|
| **需求提出人认可率** | `author_verdict = 对` 的比例 | 对 + 错（说不清不计） | **≥ 70%** |
| **定位率** | `supported` / `contradicted` 中带 `file:line` 的比例 | 断言型结论数 | **≥ 90%** |
| **漏报率（假阴性）** | 系统说 `no_evidence`、作者说错且贴出了出处 | `no_evidence` 且有明确 verdict 的条数 | **≤ 20%**，主动报 |
| **误报率（假阳性）** | 系统给出 `supported` / `contradicted`、作者说错 | 断言型且有明确 verdict 的条数 | **≤ 10%**，主动报 |
| **无法证伪异议率** | 作者说错、但贴不出出处 | 有效回执总数 | 如实报，不设目标 |
| **说不清率** | `author_verdict = 说不清` | 有效回执总数 | 如实报，不设目标 |
| **未覆盖率** | `coverage = none` 的结论比例 | 全部输出结论 | 如实报，不设目标 |

> **漏报和误报必须分开报。** 我们最容易犯的是漏报（把有证据判成没证据），最伤信任的是误报（把没证据说成有/反证）。两个数字都给，才叫没有藏。

**另外三个不计入 PPT、但内部要看**：
- 问中率：生成的 10 个问题里，作者承认"会答不上来"的比例（来自 `author_stuck`）
- 搜索轮数分布：`rounds = 1 / 2 / 3` 各占多少（说明多轮搜索有没有用）
- 版本漂移率：冻结版重跑后 `status` 与作者当时所见不一致的比例

**两个错误率都必须主动报。** 一个敢说"作者指出我们漏了 9 条、错判了 3 条"的工具，比号称 100% 准的可信十倍。

# 四、答辩（背下来）

**开场（一句话）**：
> **"所有人都在核代码写得好不好。我们核的是：要求做的，代码里到底有没有。"**

**第二句（给体感）**：
> "老师 / 大创负责人拿着一份 20 条的设计要求，只能逐条翻代码；学生简历写'支持 500 并发'，一问压测脚本就沉默。**这是同一个问题的两面**：要求方核不动，交付方说不清。"

**第三句（给方法）**：
> "我们做了一个对账引擎：识别七类条目，只对能稳定判的四类下结论。**给断言的结论必须落在文件:行；说没找到的必须给出查过哪里；连轨迹都没有的，我们照样输出，但明确标'未覆盖、不作为证据'。输出不等于证据。**"

**第四句（给数字）**：
> "在 5 份老师 / 大创需求清单 × 各 5 条 = 25 条（对 5 个项目代码，有效回执 N≈15）上，**由需求提出人本人判定**（不是我们自己标）：认可率 X%（N=X），定位率 Y%。**这是我们最容易犯的漏报率 A%，这是我们最怕的误报率 B%——两个都报了**——因为'缺失证据'和'不存在'是两件事，'我漏了'和'我错判了'也是两件事，我们不敢混。决赛补到 50 条。"

> **"由需求提出人本人判定"这几个字必须说出来。** 它一次挡掉"你自己标的标准"这个最致命的质疑。

**第五句（给最后防线 —— 如果被逼到"这不就是 linter"时用）**：
> "linter 告诉你哪里错。我们告诉你**我查过哪里**。
> 这一条：查了 4 类 14 处——压测脚本 0 处、并发原语 1 处（`app.py:12`）、worker 配置 1 处（`gunicorn.conf.py:2`）、连接池 0 处（扫过 5 处）。
> **linter 不会告诉你它查过哪里。我们会。**"

**第六句（给未来）**：
> "这个引擎有四个出口：需求核对报告、面试拷问、CI 门禁、IDE 悬浮。**我们 6 天初赛做了主渠道，顺手做了副渠道（`gap analyze` / `gap questions` 读仓库 README 的面试自检）；`--claims --spec` 双模式、SARIF 出站、CI 和 IDE 都是 roadmap，因为引擎比渠道重要。**"

**第七句（被问"这不就是 schemathesis / Pact 吗"时用）**：
> "行为契约（OpenAPI / Pact）他们做得比我们准，我们**不碰**；我们只做**能力契约**——需要一组证据、而且不知道该找哪一组的那一半。判据默认 `P95 < 300ms`，并且必须外置。"
