# 邀请人群画像与招募 SOP（初赛 6 天版）

> 用途：D0 今晚就要发出邀约。本文档回答三个问题：**发给谁、按什么顺序发、发的时候说什么**。
> 上游：[日程计划-初赛冲刺](日程计划-初赛冲刺.md) D0/D1；[施工图](施工图-对账引擎.md) §2.2–§2.5（选样本规矩 / 标注表 / 话术）。

---

## 0. 一句话判据

> **不要找"最熟的人"，也不要找"最强的人"。找"手里有需求清单、并且要验收别人"的那个人。**

需求版要的是**两份材料**：一份别人写的需求清单（老师 / 大创的要求）+ 对应的项目代码。

评委会问的是"**真实用户是谁**"。一个老师手里有一门课的设计要求，还有学生交上来的项目代码——这是一份完整样本，而且**他本来就要验收**。仓库主人本人的 README 声称降为副线：那是 `--claims` 副模式的样本，用来覆盖"自己吹的 vs 代码"这条路径。

---

## 1. 从指标反推：25 条条目需要什么样的人

### 1.1 配额（先钉死，再找人）

初赛 **5 份需求清单 × 各 5 条 = 25 条**，全部来自 4 个判定类（`architecture`/`scale`/`security` 只记录不判定，不进分母）。

| 条目类型 | 主要证据域 | 初赛最低条数 | 为什么不能再低 |
|---|---|---|---|
| `concurrency` | lock / async / thread / worker / pool | **6** | 最典型的"验收时说不清"条目，答辩必讲；低于 5 条说不出分布 |
| `performance` | benchmark / 缓存 / 索引 / 连接池 | **6** | 与 concurrency 共同支撑"能力型必须有测量证据"这条硬规则 |
| `feature` | 路由 / 函数 / 依赖 | **7** | 定位率最容易达标的类，是"断言给 file:line"的展示样本 |
| `testing` | 测试文件 / coverage 配置 / CI | **6** | 唯一能稳定产出明确 `no_evidence` 的类 |
| 合计 | | **25** | |

> **含义**：不是"随便找 5 份清单就能凑 25 条"。**每份清单必须至少含 1 条 performance 或 concurrency**，否则凑不够。
> 这就要求画像里必须有"**课程要求里写了量化指标**"的老师——这是最稀缺的一类，优先抢。

### 1.2 一位邀约对象必须提供的 4 件事（硬门槛，缺一不约）

1. **需求清单可给**：课程设计任务书 / 大创结题要求 / 验收评分表（Markdown、Word、PDF、截图都行，能转成列表即可）；
2. **代码可给**：一个或几个学生 / 团队项目（500–5000 行、Python 或 JS），且他有权转交；
3. **能当判定人**：5–10 分钟内对 5 条结论点"对 / 错 / 说不清"；
4. **能授权**：仅用于本次评测、匿名、可撤回。

### 1.3 样本结构配额（决定"像不像真样本"）

| 配额项 | 初赛目标（5 份清单 / 5 个项目） | 决赛目标（10 / 10） |
|---|---|---|
| Web 后端项目 | ≥2 | ≥3 |
| 数据处理 / 脚本项目 | ≥2 | ≥3 |
| 工具 / CLI 项目 | ≥1 | ≥1 |
| 含量化性能条目的清单 | **≥3（不可让步）** | ≥5 |
| 含测试 / 验收要求的清单 | **≥3（不可让步）** | ≥5 |
| 同一份清单贡献的条目 | 5 条（固定） | 5 条（固定） |
| 来源标注 | **每份都标"来源：某课程 / 某大创"** | 同左 |

> **防"便利抽样"质疑的准备**：明说"这是便利抽样 + 配额控制的 pilot，**5 份清单来自不同课程 / 项目，来源逐份标注**"。有配额表 + 有来源，就不是随手抓。

## 2. 需求清单特征画像（可在 5 分钟内打分）

### 2.1 打分表（门槛：≥6 分才约）

| 特征 | 分值 | 怎么判（30 秒内） |
|---|---|---|
| 量化指标：QPS / 并发 / 毫秒 / P95 / 覆盖率 / 万条 | **+3** | 搜一遍数字 + 单位，命中即给 |
| 测试或验收要求：单测 / 覆盖率 / 测试报告 / 验收表 | **+3** | 同上 |
| 功能条目清单：实现 X / 支持 Y / 可导出 Z | **+2** | 有条目式列表即给 |
| 部署 / 性能 / 安全要求：worker / 连接池 / 鉴权 / 限流 | **+2** | 有要求段即给 |
| **明显不可验收的词**："高性能""界面美观""结构良好""设计合理" | **+3 额外** | **最有价值的样本**——预检段当场就能出改写建议 |
| 附评分表 / 验收细则 | **+1** | 出现即给 |

> 打分不是为了学术严谨，是为了**今晚 20 分钟内决定找谁**。11 分以上的清单是钻石，先约。

### 2.2 今晚不细看也能用的"三问快速版"

对每个候选人心里过三问，**三问全 yes → 今晚就发**：

1. **他手里有没有一份写成条目的要求？**（课程任务书 / 大创结题要求 / 验收表）
2. **他有没有要验收的学生或团队项目代码？**
3. **他会不会 5 分钟内回你微信或邮件？**

> 第 1 问决定你有没有"要求"，第 2 问决定你有没有"证据"，第 3 问决定你的**回执率**。功能可以 vibecoding 加速，回执只能靠人。

## 3. 人群分层（按优先级抢人）

### P0 · 要验收学生的老师（今晚先约 3–4 位，**最重要**）

**画像**：本学期带课程设计 / 指导大创 / 带竞赛的任课老师、指导教师、助教。

- **为什么最优先**：
  ① **他就是 boss**：要求是他写的，"做没做"是他要判的 → 动机是 pull，不是你去推；
  ② 他手里同时有**需求清单和学生代码** → 一份邀约拿齐样本；
  ③ 他最容易给出真实证言（"这门课每年都有人把'高性能'糊过去"）。
- **典型标签**：`本学期带课设`、`大创结题指导`、`竞赛指导教师`、`课程助教`
- **今晚发几个**：3–4 个

### P1 · 要交差的项目负责人（D1 上午补 2–3 人）

**画像**：大创 / 挑战杯负责人、社团或学生会技术项目负责人、实验室项目 leader。

- **为什么**：他手里有"组员要交的东西"和一份自己列的验收清单；需求未必写成正式文档，但能口述成条目。
- **注意**：这类人往往"比较在意形象"，**邀请话术要把"抓错"说成帮忙**（见 §6.2），否则他会礼貌性说"都对"，数据全废。
- **今晚/明早发几个**：2–3 个

### P2 · 仓库主人本人（副线：`--claims` 样本 + 现场判定池）

**画像**：正在准备面试 / 答辩、README 里写了量化断言的开发者；同班、同宿舍楼、同实验室，能 20 分钟内坐到一起的人。

- **为什么**：① 副模式 `--claims` 需要"自己吹的"样本；② 这是 R1/R3 风险的唯一对冲——**回执收不回来时，约他坐你旁边当场判**。
- **注意**：这条线**不计入 5 份需求清单指标**，在材料里单列为"副模式样本 / 现场判定样本"。
- **名额**：2–3 人（不要求项目质量高，但必须 ≥500 行）

### 排除项（别浪费一次邀约）

| 排除对象 | 理由 |
|---|---|
| 只有 tutorial / 复刻项目（跟着视频敲的） | 没有"要求"，也抽不出 5 条条目 |
| 项目 <500 行 或 单文件 Hello World | 没话说，凑不出 5 条 |
| 纯静态前端页面（只有 HTML/CSS） | 4 个判定类几乎全空 |
| 只写 Java / Go / C++ 项目 | 抽取器不支持，别为难自己 |
| 明确拒绝授权或对匿名不安 | 合规风险高于收益，直接换人 |
| **本队队友本人的项目** | 利益相关，评委会质疑循环论证 |
| 只想"看热闹"、不愿花 5 分钟点三下的 | 回执率黑洞 |
| **自己反写的需求清单** | 可以用来演示，但**不进 5 份样本**，材料里必须标"自拟" |

> ⚠️ **合规表述**：赛事规则写"毕业设计和课程设计（论文）不在申报范围"，指的是**参赛作品本身**，不是评测输入。
> 为避免评委误读，材料里统一表述为"**某课程的设计要求（匿名，仅作评测输入）**"：只取要求条目本身，**不出现学生姓名、学号、论文正文与评分明细**。样本仅用于本次评测、匿名、可撤回，这句话每次邀约都要说。

## 4. 渠道与转化率（按性价比排序）

| 渠道 | 预估接受率 | 拿人速度 | 适用画像 |
|---|---|---|---|
| **任课 / 指导老师本人**（课后当面或微信） | 60–80% | 最快（当天） | P0 |
| **大创 / 竞赛指导教师、学院教务** | 30–50% | 半天 | P0 替补 |
| **课程助教 / 实验室师兄师姐（带过课设）** | 40–50% | 快 | P0 / P1 |
| **项目负责人 / 社团技术 leader 群** | 40–60% | 快 | P1 |
| **同班 / 同专业微信群**（点名问，找仓库主人） | 40–60% | 最快（10 分钟） | P2（副线） |
| **熟人转介绍**（"你导师手里有没有课设要求"） | 30% | 1 天 | P0 补充 |
| **GitHub 搜北邮学生仓库** | <10% | 慢，别指望 | 仅兜底 |

> **原则：当面 > 私聊 > 群发。** 老师在办公室/教室门口两句话就能定；群发一条基本没人理。

## 5. 今晚的发邀顺序（照着发，20 分钟）

| 序 | 目标 | 画像标签 | 备注 |
|---|---|---|---|
| 1 | 本学期带你 / 你认识课程设计的老师 | `P0 任课` | 顺带做第 1 次微访谈 |
| 2 | 大创 / 竞赛指导老师 | `P0 指导` | 顺带第 2 次访谈 |
| 3 | 带过课设的助教 / 实验室师兄 | `P0 替补` | 能代问老师要清单 |
| 4 | 要交差的项目负责人 | `P1 团队 leader` | 今晚发，明早催 |
| 5 | 上一个被拒后的替补（同渠道再点一个） | 替补 | 维持 5 人底线 |

**今晚目标：发出 ≥5 人（其中 ≥3 位老师/指导老师）、拿到 ≥2 份需求清单 + ≥2 个项目代码、完成 ≥1 次微访谈。**
**明早（D1 上午）目标：累计发出 5 份清单 + 5 个项目代码的邀约，材料到手 ≥3 份。**

## 6. 邀约 SOP

### 6.0 五步

1. **先看材料 30 秒**（需求清单打分 ≥6 或三问全 yes）；
2. **当面/私聊，第一句就说到具体材料**（"我看了您这学期的课程设计任务书"）；
3. 发**授权 + 三按钮承诺**（五分钟、只判对错、匿名可撤回）；
4. **顺带问一句微访谈问题**（拿到 B 端需求验证，见 §7）；
5. 立刻**登记追踪表**（§9），当天不回就在 D+1 催一次，D+2 换人。

### 6.1 首次邀约话术（对老师 / 项目负责人，可直接复制）

> "老师您好，我在做一个工具：**输入一份课程设计要求 + 学生项目代码，自动核对'要求做的'和'代码里做了的'之间的缺口**，顺带指出哪几条要求本身没法验收。
> 想跟您借两样东西：一份您这学期的课程设计/大创要求（**只要要求条目，不要学生姓名学号**），和 1–2 个学生项目代码。
> 跑完我把 5 条结论发您，您只需点 **对 / 错 / 说不清**，五分钟。
> **如果它判错了，一定告诉我哪错了**，这对我最重要。
> 代码我只看、不出报告正文、不公开、不写姓名，只用于这次比赛评测，随时可以让我删。"

### 6.2 对"在意形象"的项目负责人（P1 专用改写）

> 别用"你的组员有问题"这种框架，改成：
> "**我这工具可能误判你**，想请你帮我抓它的错。你越挑得出毛病，我这工具越有用。"

### 6.3 催收话术（D+1 用，只催一次）

> "老师打扰一下，就问一句：那 5 条您方便的时候点一下？我这周五要交，还差几份回执，您要是不方便我换个人也行，别耽误您。"

> **"你要是不方便我换个人也行"这句必须说**——它会显著提高回复率，也保护你的时间预算。

### 6.4 被拒 / 沉默的处理

| 情形 | 动作 |
|---|---|
| 老师太忙 / 不愿意 | 一句"没事，打扰了"，立刻换替补（不停留、不再解释） |
| 学生代码不愿意公开 | 只给需求清单 + 目录树 + 指定 3 个文件，其余不读（如实写进报告局限） |
| 同意但一直拖到 D4 | **转现场**：约他 5 分钟，你跑一遍他当场判（这一步比催有用十倍） |
| 只能给清单、给不了代码 | 记作"预检样本"（只做可判定性预检，不参与对账比率），继续找代码 |

## 7. 微访谈脚本（15 分钟，一次拿三样东西）

**这三问的顺序不能换**——先问验收痛感，再问最有风险的条目，最后问信任。

| # | 问题 | 拿到什么 |
|---|---|---|
| Q1 | "您这门课 / 这个大创的验收，最费劲的是哪一条？" | **B 端需求验证**（原来 S2"没人用"降级后要验的就是这个）。答"没有费劲的"就是红灯票 |
| Q2 | "您觉得学生最容易'看起来做了、其实没做'的是哪一条？" | **一条高质量需求条目**（比从文件里抽的更真），直接进 25 条 |
| Q3 | "如果工具说这条没证据，您会拿它当验收依据吗？" | **信任校准**：会用 = 措辞安全；不会 = 你的结论太重或太虚 |

**记录格式（一行一人，别写小作文）**：
```
S02 | 任课老师 | Q1=并发和性能没法验 | Q2="支持 500 并发" | Q3=会参考（"我本来也只能靠问"）
```

**红灯判定**：前 6 次访谈中若 **≥4 位老师/负责人说不出"哪条最难验收"，或明确表示不会用工具验收** → D3 当天把主叙事退回 `--claims` 副模式（面试自检），PPT 第一页换图，不等到 D6。

## 8. 授权与合规（一句话，但要留痕）

- 文字/邮件都要包含三要素：**仅用于本次评测、完全匿名、可随时撤回**；
- **微信/邮件文字留存**（不要只有口头）——截图进 `codearts_proof/` 或单列 `consent/`；
- 需求清单**只取条目本身**，去掉学生姓名、学号、评分明细与论文正文；
- 入库前做**密钥/隐私扫描**（`.env`、`*.pem`、姓名学号、手机号、数据库口令）；
- **报告不附带原始代码**，只给 `file:line` 与必要片段（≤3 行）；
- 材料里统一写"某课程的设计要求（匿名，仅作评测输入）"。

## 10. 六天里的招募节奏（与日程对齐）

| 时间 | 动作 | 目标 |
|---|---|---|
| **D0 今晚** | 当面/私聊发 5 人（≥3 位老师，顺序见 §5），拿 2 份清单 + 2 个代码，做 1 次微访谈 | ≥5 发出 / ≥2 清单 / ≥2 项目 |
| **D1 上午** | 补发至 5 份清单 + 5 个项目；对 S01–S03 做微访谈 | ≥5+5 意向 / 访谈 ≥3 |
| **D1 下午** | 需求清单打分，锁定 5 份清单，按配额补齐类型缺口 | 5 份清单定档 |
| **D2** | 催一次未回的；访谈累计 ≥4 | 材料齐 + 1 个备用 |
| **D3** | 把 D1–D2 的结论**现场**给 3 位提出人判（不等线上） | ≥3 份回执 / 访谈 ≥6 + 红灯判定 |
| **D4** | 追剩余回执；不回的当场约 | ≥4 份回执累计 |
| **D5** | 回执定格（或改现场判定），标记"现场判定"样本 | 数字可出 |
| **D6** | 只做材料，不再招人 | — |

## 11. 常见坑（都是踩过的）

1. **只找学生、不找老师** → 缺 boss 视角，"真实用户"这几分拿不到，且需求清单只能自拟。
2. **找"写得最漂亮"的清单** → 条目全是可验收的，`❓ 无法验收` 一条都出不来，预检这个卖点展示不了。**要留至少 1 份含模糊表述的清单。**
3. **拿不到真清单就自己写** → 必须标"自拟"，且**不进 5 份样本**；否则等于自己出题自己考试。
